Tenant location tokens live in integration_credentials.api_key and refresh_token; company installation tokens live in oauth_installations.access_token and refresh_token. The existing resolver reads stored credentials before deciding whether the token needs refreshing. The location and company runtimes use a five-minute pre-expiry threshold; refresh occurs on demand during credential resolution, including provider operations from Queue consumers. The scheduled entry point handles reservation dispatch; no periodic OAuth refresh was verified. Refresh uses a lease and persists the new access token plus the rotated refresh token (or preserves the current refresh token when absent). GHL writes require the Core cipher. AES-256-GCM binds ciphertext to the owning scope and field; the v1 envelope records the key label used to decrypt it. A legacy field is readable only when the compatibility flag is exactly true.

For this recovery: CORE_CREDENTIAL_ENCRYPTION_KEYS is a Worker secret containing a JSON version-to-Base64 mapping of 32-byte AES keys. CORE_CREDENTIAL_ACTIVE_KEY_VERSION must be ghl-v1 and present in that mapping. CORE_CREDENTIAL_LEGACY_READS_ENABLED must temporarily be true. Leave the separate Meta keyring untouched. Allowing plaintext reads alone could let a refresh rotate its token at GHL before local persistence fails.
